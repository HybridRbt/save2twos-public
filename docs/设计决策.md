# 设计决策

## 文本与原生标签

正文使用 `draft.content` 原样发送，不添加来源文字、时间文字或 hashtag，也不从正文提取标签。来源使用固定的原生 `drafts` 标签，并全量合并 `draft.tags`。固定标签在首位，其余保留原顺序；去掉首尾空白、忽略空值，按大小写不敏感去重，保留首次拼写。不修改原草稿。

## 创建时刻与日期归档

`draft.createdAt` 只提供真实时刻，不能据此推断创建地时区。`created` 使用含毫秒的 ISO 时间；`list` 使用该时刻在确认时区内的日期。日期计算使用 IANA 时区规则，包括历史夏令时，不使用固定 UTC 偏移，也不截取 UTC 日期。

创建后 0–30 分钟内视为新记录，按当前设备时区处理；设备时区变化时确认。更早或未来时间的草稿选择创建时区。上海、芝加哥是快捷候选，其他地区填写 IANA 名称。这是明确的交互规则，不是地理定位。

## 暂时沿用旧稿时区

旧稿可单次发送，也可沿用所选时区至设备当地下一次午夜或持续 168 小时。午夜按实际日期边界计算，兼容 23/25 小时夏令时日；再次发送不延长期限。设备时区变化、到期或偏好无效后恢复询问，新记录始终使用当前设备时区。

批量旧稿可能来自不同地区。只有确认适用同一创建时区时才应暂停询问；需要逐条确认时使用单次发送或备份重置本地状态。

## 本地状态与失败

版本 1 的单条本地状态保存设备时区和发送开始时间，可选保存旧稿提醒偏好；不存正文、API key 或逐篇历史。旧版本不含偏好时无需迁移。状态保留到成功替换或手动移走，备份由使用者自行清理。

仅 HTTP 201 后写入状态。取消和失败不更新；远端成功但本地保存失败时明确提示已发送，避免诱导重复创建。网络结果不明时不自动重试。

## 保持条目紧凑

早期试验验证过附属 `note` 和 `drafts://` 原稿链接，但客户端展开附注和链接卡片使普通记录过于拥挤。因此新建请求不再包含 `note` 或 `url`，也不依赖草稿 UUID。来源通过原生标签表达，需要时在 Drafts 搜索原稿。

重复发送始终新建，不引入 UUID 到 Twos ID 的映射、不做更新、去重或双向同步。既有条目不追溯修改。Twos 原生时间显示可能随查看设备时区变化，正文不固定时间文字。
